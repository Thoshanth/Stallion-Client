# Build a Production-Ready Dynamic Gym Website + CMS for Stallion

Build a modern, responsive, secure and scalable gym website for **Stallion** with a separate owner/manager CMS dashboard.

The system must be designed from the beginning as a **dynamic content management platform**, not as a static website.

The most important business requirement is:

> Gym owners and authorized staff must be able to manage trainers, events, event galleries, branches, programs, reviews, pricing, FAQs, images and other website content without touching source code, databases or APIs.

## 1. Technology Stack

Use:

* Next.js
* TypeScript
* Tailwind CSS
* shadcn/ui
* Node.js
* Express
* TypeScript
* MongoDB
* REST API
* Zod validation
* Secure authentication
* Role-Based Access Control
* Cloudinary or an equivalent image-storage/CDN service
* Git/GitHub

Keep the architecture modular so additional gym services can be added later without rebuilding the system.

## 2. Application Structure

Create two major applications/interfaces:

### Public Website

Used by customers and visitors.

### Admin CMS

Used by Stallion owners, managers and authorized trainers.

Recommended structure:

```text
project/
├── frontend/
├── backend/
├── shared/
├── docs/
└── README.md
```

Keep frontend and backend logically separated.

## 17. Role-Based Access Control

Implement:

### SUPER_ADMIN

Full access.

### OWNER

Access to website content, trainers, events, branches, programs, gallery, reviews, pricing and FAQ.

### MANAGER

Limited content-management permissions.

### TRAINER

Only access resources specifically assigned to them, such as their profile/classes/events.

Authorization must be enforced on the backend.

Do not rely only on hiding frontend buttons.

## 18. Authentication

Implement secure authentication.

Requirements:

* Password hashing using Argon2id or bcrypt
* Secure session/token handling
* HTTPS-ready architecture
* Login rate limiting
* Input validation
* Secure logout
* Password reset architecture
* No passwords returned through APIs
* No secrets exposed to frontend code

Never store plaintext passwords.

## 19. Image Architecture

Do NOT store large image binaries inside MongoDB.

Use external object/image storage and CDN.

Flow:

```text
User upload
→ Authentication
→ File validation
→ Size validation
→ Image processing
→ Compression
→ WebP/AVIF where appropriate
→ Multiple responsive sizes
→ Image storage/CDN
→ URL/metadata stored in MongoDB
```

Implement:

* Allowed MIME types
* File-size limits
* Image dimension validation
* Duplicate/reuse strategy where practical
* Optimized delivery
* Secure upload handling

The architecture must remain suitable for large amounts of gym photography.

## 30. Important Final Requirement

The project must be built as a **real dynamic CMS-backed website**, not merely as a visual prototype.

Demonstrate this workflow:

```text
Owner logs into CMS
        ↓
Adds a new trainer
        ↓
Uploads trainer photo
        ↓
Publishes trainer
        ↓
Backend validates request
        ↓
Database stores trainer information
        ↓
Image storage stores optimized image
        ↓
Public API returns trainer
        ↓
Trainer automatically appears on website
```

Repeat the same principle for:

* Events
* Event galleries
* Branches
* Programs
* Reviews
* Pricing
* FAQ

The final result should be maintainable, secure, scalable and usable by non-technical Stallion gym owners.
